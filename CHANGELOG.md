# Changelog

## [Unreleased]

### Added
- The SWE pipeline's test-coverage target is now configurable per-target via a `coverage_threshold` key in the target's registry config (defaulting to 100%). The threshold drives the `C-coverage` stage (a coverage issue is created when coverage falls below it), the `C-review`/`C-doc-sync`/`C-publish` gates (which only proceed once coverage meets the threshold), and the issue-fix plugin's SELECT/GATE coverage verification (the threshold is stored on the task at SELECT time and enforced at GATE time).
- Added an execution log: when the top-level `log_file` config option is set, the pipeline writes a structured JSONL log recording every tick and stage evaluation. Entries include a unique tick ID (`YYYYMMDD-HHMMSS-XXXXXX`), `tick_start`/`tick_end`/`stage` events, durations, stage results, and the resolved action command. Relative paths are resolved relative to `workspace_dir`, and the log rotates at 10 MB with up to 5 backups (`.1`–`.5`).
- Added a "Recent Activity" section to the webui dashboard, backed by a new `GET /api/log?config=<name>&limit=<1-500>` endpoint. It parses the pipeline's JSONL execution log (resolved from `config.log_file` relative to `config.workspace_dir`), groups entries by `tick_id`, and renders expandable tick cards showing tick ID, target, final status, duration, stage/action/failure counts, the dry-run flag, and per-stage result badges with `action_command`, `stdout`, and `stderr`. Returns an empty list when no `log_file` is configured, the file is missing, or it contains no ticks.

### Changed
- Stages with a `modes` restriction are now skipped when no mode is set (no `mode_file` configured, mode file missing, or invalid JSON). Previously, a `None` mode meant the `modes` restriction was ignored and the stage was active; now a stage with a `modes` list is only active when the current mode is explicitly set to one of its allowed modes.
- `_build_queue_handler` in the SWE prompt builders now raises a `ValueError` when `queue_dir` is missing or empty, instead of silently defaulting to an empty string (which previously resolved to the current working directory). This affects the `queue_fix_agent`, `queue_coder_agent`, and `queue_review_agent` actions, which now require `queue_dir` to be configured either in the stage action params or in the pipeline's top-level `action_handler` config.
- The webui's FastAPI app is now built lazily via a `_build_app()` function, with the `fastapi`/`pydantic` imports deferred inside it. The module-level `app` is set via `try: app = _build_app() except Exception: app = None`, so `webui/app.py` can be imported even when the web stack is unavailable or broken (missing fastapi/pydantic, or any other error during app construction).
- Action handlers now apply default timeouts when `timeout_seconds` is not specified: command and subprocess actions default to 300 seconds (5 minutes), and http_request actions default to 30 seconds.
- The `http_request` action handler's `resolve_private_ip` parameter has been renamed to `pin_to_validated_ips` to reflect its actual semantics: it controls whether the connection is pinned to the validated public IPs (DNS rebinding protection), not whether private IPs are resolved and blocked (which always happens regardless of this parameter). The old `resolve_private_ip` name is kept as a deprecated alias for backward compatibility; when both are present, `pin_to_validated_ips` takes precedence.
- `ActionResult` now carries a `command` field (defaulting to empty string) that records the resolved action command/prompt/url/callable. A new `resolved_command(action, context)` helper resolves the action's command string (with template variables substituted, falling back to the raw template on substitution failure), and all built-in action handlers (`command`, `subprocess`, `custom`, `http_request`) populate `result.command`. This value is used by the execution log's `action_command` field on stage entries.
- Execution-log entry timestamps and tick IDs (`YYYYMMDD-HHMMSS-XXXXXX`) are now generated in UTC (timezone-aware, via `datetime.datetime.now(datetime.timezone.utc).isoformat()`) instead of the naive local time previously used, so log timestamps are consistent across timezones.
- The SWE pipeline's `C-pr-title` stage now instructs the PRReviewAgent to generate both a PR title **and** a well-structured PR body (with `Summary`, `Changes`, and `Testing` sections) instead of only a title. The agent writes both to a single JSON marker file renamed from `pr_title.json` to `pr_meta.json` (format `{"title": "...", "body": "..."}`), and the `C-publish` stage reads both fields from that marker when opening the PR. The previously auto-generated boilerplate body (`_build_pr_body`) is now used only as a fallback when the agent-generated marker is missing or contains no body. The `C-pr-title`/`C-pr-publish` triggers and the example `configs/swe_pipeline.json` were updated to reference the new `pr_meta.json` marker name.

### Fixed
- Chaining now re-derives the target state after a stage invalidates markers from other stages (via its `invalidates` config), so a stage whose markers were invalidated by a prior (possibly chained) stage becomes actionable again within the same tick. Previously, the target state was stale during the chaining phase, so invalidated stages were never re-evaluated in the same tick. The re-derivation happens in both the normal execution path and the chaining loop, and is only performed when the stage's `invalidates` list is non-empty (re-deriving otherwise discards in-memory overrides such as the rejection re-process flag).
- The `http_request` action handler now always resolves the hostname and blocks requests that resolve to private/reserved IP addresses, even when `resolve_private_ip` is set to `false`. Previously, setting `resolve_private_ip: false` skipped DNS resolution and private-IP validation entirely, so a hostname that resolved to a private IP (e.g. `internal.corp` → `10.0.0.5`) would bypass SSRF protection. `resolve_private_ip` now only controls whether the connection is pinned to the validated public IPs (to prevent DNS rebinding) or left to normal DNS resolution at connect time; private IPs are always blocked.
- The issue store's `create_issue()` now raises a `ValueError` (refusing to overwrite) when a different issue ID sanitizes to a filename that is already used by an existing issue (a filename collision), instead of emitting a `UserWarning` and silently overwriting the existing issue file.
- The `http_request` action handler now pins the HTTP connection to the IP address that was validated during the SSRF check (when `resolve_private_ip` is enabled and the host resolves to public IPs only), instead of letting `urllib` re-resolve the hostname during the actual request. This closes a DNS rebinding / time-of-check-time-of-use (TOCTOU) vulnerability where an attacker who controls DNS could return a public IP during the validation check and a private IP during the actual request, bypassing the SSRF protection. The original hostname is preserved for TLS SNI and certificate validation on HTTPS.
- The `http_request` action handler now manually follows HTTP redirects (up to 5 hops) and re-validates SSRF protection (URL scheme and private-IP checks) on every redirect hop, instead of letting `urllib` follow redirects automatically. Previously, `urllib.request.urlopen` followed redirects automatically, so an attacker could redirect a request to a private/reserved IP address (e.g. `localhost`, `169.254.169.254`) and bypass the SSRF protection that only validated the original URL. Redirects without a `Location` header now return an error, and exceeding the 5-hop redirect limit returns `"Too many redirects (max 5)"`. For POST requests, 301/302/303 redirects switch to GET (matching urllib's default behavior), while 307/308 redirects for POST are not followed.
- The `http_request` action handler now strips sensitive headers (`Authorization`, `Cookie`, `Proxy-Authorization`, and any header whose name contains a credential keyword such as `auth`, `token`, `key`, `secret`, `credential`, or `password`) when following a redirect to a different host than the original URL, so credentials are never leaked to a cross-host redirect target. Non-sensitive headers (e.g. `Content-Type`, `Accept`, `X-Request-ID`, `X-Forwarded-For`) are preserved, and redirects that stay on the same host keep all headers.
- The SWE plugin's `run_c_pr_status` action now returns an `ActionResult` with `success=False` and `stderr="PR marker file not found"` when the `pr_published.json` marker file is missing, instead of raising a `FileNotFoundError`. This prevents the `C-pr-status` stage from crashing when the PR publish marker has not yet been created.
- The SWE plugin's `run_a5_bandit`, `run_a6_vulture`, and `run_a8_radon` actions now check `context.target_dir.is_dir()` (instead of `(context.target_dir / context.target).is_dir()`) when deciding whether to scan the target directory or the current directory. Previously the incorrect path check meant the default scan target was almost never the target directory, so these actions could scan the wrong path when no custom `security_cmd`/`deadcode_cmd`/`complexity_cmd` was configured.
- The issue-fix plugin's `run_gate` now prints an ERROR message, writes a failed gate result file (containing `task_id`, `gated_at`, `issue_type`, `passed: false`, and an `error` field describing the checkout failure) to the task directory's gate result file, and returns `False` (aborting the gate) when `git checkout` of the task branch fails during verification, instead of continuing to run verification commands on the wrong branch.
- The SWE `queue_fix_agent` action now writes its deduplication marker (`queued_for_{report_stem}.marker`) only after the agent is successfully queued (and only when not in dry-run mode), instead of before queueing. Previously the marker was written before the queue action, so a queue failure would leave the dedup marker in place and the work would be lost (the stage would appear queued when it wasn't). Now a failed queue action leaves no dedup marker, so the work is retried on a subsequent tick.
- The issue-fix plugin's `_is_task_stale` now falls back to the task file's modification time (mtime) when the task's `created_at` field is missing or unparseable (corrupt JSON, invalid date), instead of treating the task as immediately stale. This prevents valid in-progress tasks from being prematurely cleaned up just because they lack a `created_at` timestamp.
- The issue-fix plugin's `_read_task` now returns `None` when the task's `task.json` file is missing or corrupted (unreadable or invalid JSON), instead of raising an exception. Callers handle the `None` result gracefully: `_cleanup_stale_task` treats a missing/corrupt task as an empty dict (falling back to the task directory name for the task id), `run_gate` (the GATE stage) cleans up the task directory when its `task.json` is unreadable (printing a message and invoking `_cleanup_stale_task`), and `run_issue_fix_state_machine` cleans up a corrupted active task and selects a new one instead of crashing. In dry-run mode these paths report what they would do without mutating state.
- The SWE plugin's `_find_active_task` helper now selects the most recently modified unfinished task for a repo (by the `task.json` file's modification time, falling back to the path string for tie-breaking) instead of using lexicographic path ordering, so tasks like `task-github-10` are correctly preferred over `task-github-9` when the former was modified more recently.
- The issue-fix plugin's stale-task cleanup now uses `git reset --hard HEAD` instead of `git clean -fd`, so untracked files (e.g. `.venv`, generated artifacts) are preserved when a stale task's git state is reset.
- The issue-fix plugin's stale-task cleanup (`_cleanup_stale_task`) now verifies that a task belongs to the expected repo before deleting it. It checks the task's `repo_name` field in `task.json`: if present, it must equal the expected repo name, otherwise cleanup is refused with an ERROR message (e.g. "task at ... belongs to repo 'X', not 'Y' — refusing cleanup") and the task is left untouched. When `repo_name` is absent (or `task.json` is corrupt/unreadable), it falls back to verifying the task directory name format `{date}_{safe_repo}_{task_id}`, requiring the safe-repo slug in the directory name to match the expected repo (otherwise cleanup is refused with "cannot verify task ... belongs to repo ... — refusing cleanup"). This prevents a stale-task cleanup from deleting a task directory that belongs to a different repo. Additionally, `_cleanup_orphaned_task_dirs` now matches the repo component of task directory names exactly (the full safe-repo slug, not a prefix), so a repo whose name is a prefix of another repo's name is no longer wrongly matched, and task directories without a repo component are skipped.
- The issue-fix plugin's stale-task cleanup (`_cleanup_stale_task`) now always derives the git branch to delete from the task ID (`_task_branch_name(task_id)`, e.g. `swe-pipeline/task_{task_id}`) instead of trusting the `branch` field in `task.json`. Previously a tampered or corrupt `branch` field (e.g. one set to `main` or another repo's branch) could cause the cleanup to delete a git branch belonging to a different repo.
- Chained stage failure now reported in TickResult with ACTION_FAILED status and the failed stage ID.
- Chained stage on_fail actions are now executed when a chained stage fails (previously silently ignored).
- Chained stage failure message no longer has a trailing colon when the action produces no output.
- StageState.is_actionable now treats a rejected stage as actionable when max_rejections=0 (rejection tracking disabled).
- mode_file and config_file paths are now resolved relative to workspace_dir instead of the current working directory.
- http_request action handler now rejects non-http/https URL schemes (e.g. file://) to prevent arbitrary file access.
- Async custom actions (e.g. queue_fix_agent, queue_coder_agent, queue_review_agent) no longer create their completion marker immediately; the pipeline now respects `data: {"async": true}` returned by custom actions and defers completion to the external agent.
- Custom action handler now passes through `ActionResult` return values instead of stringifying them.
- `ActionResult.data` now defaults to `{}` when `None` is passed, fixing an AttributeError when accessing `result.data.get('async')`.
- Async chained stages now create a processing marker (with `retry_count=0` and the result data merged in) to prevent duplicate agent queueing.
- Non-chained async custom actions now create a processing marker (with `retry_count=0` and the result data merged in) so they are not re-triggered on every tick, preventing duplicate agent queueing.
- `_handle_stale` now returns a DRY_RUN result before deleting processing markers or re-queueing when in dry-run mode, and correctly reports "Would give up" when the retry limit is reached.
- `_handle_stale` now returns ACTION_FAILED (and runs `on_fail`) when the re-executed action fails, instead of reporting ACTION_EXECUTED.
- `FileLock.__enter__` now raises `RuntimeError` when the lock cannot be acquired instead of silently continuing.
- MarkerSpec objects are no longer mutated in-place when the pipeline creates processing markers (e.g. for async actions, chained stages, or stale re-queueing); the pipeline now uses `dataclasses.replace()` to build new marker specs, preventing shared config objects from being modified during tick execution.
- Bumped setuptools build requirement to >=83.0.0 to address PYSEC-2026-3447.
- Rejection marker is now cleared only when the stage's work actually completes (when the completion marker is created), not when a `queue_agent` action re-queues work below `max_rejections`. Applies to both regular and chained stages.
- Rejection count now increments only when the stage's trigger actually fires (i.e., the stage will be re-processed this tick), rather than on every tick regardless of the trigger.
- FILE-type rejection markers never accumulate a rejection count; when used with `max_rejections`, the marker is simply deleted (FILE markers can't store data).
- Rejection count is now written back into the JSON rejection marker below `max_rejections` so it accumulates across ticks instead of being lost when the marker is cleared.
- `retry_count` is now read from the actual on-disk processing marker data (`stage_state.processing_data`) instead of the static config content, so it is correctly preserved across re-queues by a `queue_agent` action.
- Pipeline now stops chaining when a custom action returns `data: {"async": true}`, matching `queue_agent` behavior; previously async custom actions would incorrectly chain to the next stage.
- `ActionHandlerConfig.from_dict` now treats an empty `params: {}` dict as present (not missing), so other top-level keys are no longer incorrectly merged into `params`.
- `ActionHandlerConfig.from_dict` now raises a `ValueError` with a clear message when the required `type` field is missing, instead of an unhandled `KeyError`.
- `TickResult.__str__` now includes stderr output, so captured tracebacks are shown to the user.
- `tick()` exception handler now reports the actual failing target instead of `*`.
- `tick_all()` now continues processing remaining targets even if one raises an exception, and captures the traceback in the returned TickResult's stderr field.
- `MarkerSpec.resolve_path` now rejects path traversal (`..` segments) and absolute paths that escape the workspace.
- `MarkerSpec.resolve_path` now resolves the base directory (following symlinks) before the traversal check and returns the fully-resolved path, preventing a TOCTOU race where a symlinked base directory could be swapped between the check and use.
- `MarkerSpec.resolve_path` now returns the symlink path itself (not the fully-resolved target) for SYMLINK-type markers, so callers can operate on the symlink entry itself rather than following an existing symlink to its target; for other marker types (FILE, JSON) it continues to return the fully-resolved path.
- Template substitution failures in `command`-type actions, `conversation_queue`, and `run_diagnostic` now return an `ACTION_FAILED` result with the error message instead of silently using the unformatted template.
- The issue store's YAML frontmatter parser (_parse_value) now correctly parses boolean values (true/false/yes/no) and null values (null/none/~) instead of treating them as truthy strings. This fixes config toggles like enabled: false being treated as truthy when read from issue frontmatter.
- The issue store's YAML frontmatter parser (parse_frontmatter) now correctly handles quoted values containing colons (e.g. `title: "Fix: Login bug"`), instead of truncating the value at the first colon.
- The SWE plugin now normalizes naive datetime strings to UTC when parsing timestamps from GitHub session files, review issue frontmatter, and queued markers (doc_sync, pr_review), preventing comparison errors and incorrect behavior when naive datetimes are compared against timezone-aware datetimes.
- The SWE plugin's `_git` helper now enforces a timeout (default 60 seconds) on git subprocess calls, so a hung git command can no longer block the pipeline indefinitely. On timeout a `TimeoutExpired` is raised (with stdout/stderr decoded to str), and callers (`ensure_phase_a_branch`, `commit_phase_a_change`, `run_c_doc_sync`) now handle `TimeoutExpired` gracefully.
- When a stale sync action (command, subprocess, or custom) is re-executed successfully, the pipeline now creates the stage's produced markers and completion marker, clears the rejection marker, and invalidates other stages' markers — matching the behavior of the normal (non-stale) execution path. Previously, re-executed stale sync actions never created their completion marker, so the stage would be re-triggered on every subsequent tick.
- The `run_diagnostic` action now returns `success=False` when the underlying diagnostic command exits with a non-zero exit code (e.g. a linter finding errors, a test suite failing, a security scanner finding vulnerabilities), instead of always returning `success=True`. The report file is still written regardless of the exit code.
- The `run_a9_dep_audit` action (pip-audit dependency scanner) now proceeds to parse the diagnostic output and create dependency-audit issues even when the diagnostic command exits non-zero (the normal case when pip-audit finds vulnerabilities). Previously it returned early when the command failed, so vulnerabilities were never turned into issues. Success is now conditional: `result.success` is set to `True` only when dependency-audit issues were actually created (`issues_created > 0`). If the audit fails (command exits non-zero) but no issues could be created from the output, the function preserves the failure by setting `result.success = False` and appending the message "No vulnerability issues could be created from failed audit output" to stderr, instead of unconditionally forcing success and masking genuine failures.
- The `marker_state` trigger's comparison operators (`lt`, `lte`, `gt`, `gte`) now return `False` (instead of raising a `TypeError`) when the JSON field value's type does not match the expected value's type (e.g. comparing a string field against an integer value), so a type mismatch no longer crashes the pipeline.
- The SWE plugin's `sync_session_mode` pre-tick hook now treats a completed GitHub session like an idle session: it writes `{"mode": "default"}` to the mode file and returns `True` so the tick proceeds normally (it is no longer skipped for completed sessions), so a completed session no longer permanently blocks the target. The `detect_b1_issue_gathering` trigger now uses a completed session's `completed_at` timestamp as its recheck reference point (idle sessions use `checked_at`), so B1 issue gathering can fire again once the `GITHUB_RECHECK_SECONDS` interval has elapsed since the session completed.
- The `_PinnedHTTPConnection` and `_PinnedHTTPSConnection` classes now raise `OSError('connection failed')` instead of potentially raising `None` when no validated IP connection could be established, fixing a mypy type-safety issue where `raise last_err` could raise `None`.
- The SWE plugin's issue-scanning helpers (`_git_issue_already_ingested`, `_count_open_review_issues`, `_open_issue_count`, `_has_open_coverage_issues`, `_count_done_issues`, `_count_done_review_issues`, `_find_previous_review_sha`, and the `detect_c_coverage_issue`/`detect_c_review_issue` duplicate checks) now parse each issue's full YAML frontmatter via `parse_frontmatter()` instead of reading only the first 800 characters and extracting metadata fields (`source`, `github_number`, `status`, `type`, `created_at`) with regex. Previously, metadata fields that appeared after the 800-character mark in the frontmatter were missed, so issues with long frontmatter could be misclassified (e.g. an already-ingested GitHub issue not detected as ingested, open review/coverage issues not counted, or an existing non-discarded issue not blocking a duplicate). Now all frontmatter fields are read correctly regardless of their position in the file.

### Security
- The Web UI's enable/disable toggle endpoint (`POST /api/toggle`) now validates that the toggle path (the pipeline's `config_file`) resolves within the pipeline's `workspace_dir` or the `CONFIGS_DIR` before writing, using a new `_is_path_within` helper that resolves symlinks on both paths (via `Path.resolve()`) and checks containment with `is_relative_to`. A toggle path that resolves outside both safe directories (including via a symlink pointing outside) is rejected with an HTTP 400 error ("Toggle path is outside the workspace or configs directory"). Previously the endpoint would write `{"enabled": true|false}` to whatever path the config specified with no authentication and no path validation, allowing arbitrary file writes to paths outside the workspace/configs directories.
- The SWE plugin's GitHub API calls (`_gh_api_get_list`, `_gh_api_post`, `_gh_api_patch`, and `run_c_pr_status`) now use a custom HTTP opener built with a `_NoRedirectHandler` (an `urllib.request.HTTPRedirectHandler` subclass whose `redirect_request` always returns `None`), which prevents automatic redirect following. This ensures the `Authorization` header is never sent to a redirected URL, so the authorization token cannot be leaked to an attacker-controlled host via a malicious or compromised GitHub API response.
- Addressed bandit findings: added nosec annotations for intentional subprocess/shell usage, resolved git binary via shutil.which, and validated HTTP URL schemes.
- `http_request` action handler now redacts URLs (removes userinfo and query params) in result data to avoid leaking sensitive information.
- Template-substituted variables (`target`, `target_dir`, `workspace_dir`, and target config values) are now shell-quoted with `shlex.quote()` before substitution into `command`-type actions and `run_diagnostic` commands, preventing command injection when values contain shell metacharacters.
- `command`-type actions and `run_diagnostic` now execute commands via an argument list (`shell=False` using `shlex.split()`) instead of a shell, preventing shell injection through template-substituted values.
- The `run_lint_autofix` action in the SWE plugin now executes its command via an argument list (`shell=False` using `shlex.split()`) instead of a shell, preventing command injection through template-substituted values; invalid commands return an ACTION_FAILED result.
- The `_run` helper in the issue-fix plugin now executes commands via an argument list (`shell=False` using `shlex.split()`) instead of a shell, preventing command injection through template-substituted values; invalid commands return an error result.
- The issue-fix plugin's prompt builders (`_build_coder_prompt`, `_build_coverage_prompt`, `_build_review_prompt`, and the closing-loop instructions) now shell-quote the repository directory path with `shlex.quote()` before embedding it in generated prompts (e.g. `cd {repo_dir} && ...`), preventing command injection when the repo directory path contains spaces or shell metacharacters.
- `run_diagnostic` now validates command config values (e.g. `test_cmd`, `lint_cmd`) and rejects values containing shell metacharacters.
- `format_template` now raises `ValueError` on substitution failure (missing key, bad format) instead of silently returning the unformatted template; callers return an `ACTION_FAILED` result with the error message.
- Fixed prompt template escaping in SWE plugin and prompt builders so JSON literals embedded in prompts render correctly after `.format()` substitution.
- Conversation queue handler now sanitizes agent names (replacing any non-alphanumeric, underscore, dot, or hyphen character with `_`) before using them in queue filenames, and validates the resolved queue file path with `.resolve()`/`is_relative_to()`; queue files that would escape the queue directory now raise a `ValueError`, preventing path traversal attacks.
- File-based trigger conditions (`file_missing`, `file_exists`, `file_older_than`, `marker_state`) now validate their `path` against path traversal, rejecting `..` segments, absolute paths, and paths that resolve outside the workspace/base directory (including via symlinks), raising a `ValueError` for invalid paths.
- The `queue_empty` trigger now validates its `queue_dir` value against path traversal, rejecting `..` segments and paths that resolve outside the base directory (including via symlinks), raising a `ValueError` for invalid paths.
- The issue store's `create_issue()` now rejects issue IDs containing `..` (e.g. `../../evil`, `foo..bar`, or `..`) by raising a `ValueError`, instead of sanitizing them; single dots remain allowed (e.g. `foo.bar`). For other characters, the issue ID is sanitized before use as a filename: any character that is not alphanumeric, dot, underscore, or hyphen is replaced with `-` (leading/trailing dashes stripped), and an empty sanitized ID falls back to `issue`. The resolved path is validated with `.resolve()`/`is_relative_to()`; a filename that would still escape the issues directory raises a `ValueError`. This prevents path traversal attacks via malicious issue IDs (e.g. absolute paths like `/etc/passwd`).
- Target names are now validated to prevent path traversal: `Pipeline.tick()`, `Pipeline.tick_all()`, `Pipeline._tick_single()`, `Pipeline.status()`, and the CLI `--reset-stage`/`--reset-target` options reject target names containing `..` segments or absolute paths (raising a `ValueError` or returning exit code 1 for the CLI), preventing path traversal attacks via malicious target names.
- The `command` and `subprocess` action handlers now validate that the `cwd` parameter resolves within the pipeline's workspace directory. A `cwd` that escapes the workspace (via `..` segments, absolute paths, or symlinks) is rejected with an `ACTION_FAILED` result (`success=False` with stderr `"cwd escapes workspace directory: {cwd}"`), preventing actions from executing commands or scripts outside the workspace.
- `Pipeline.__init__` now validates that the `ConversationQueueHandler`'s `queue_dir` resolves within the pipeline's workspace directory. A `queue_dir` that escapes the workspace (via `..` segments, absolute paths, or symlinks) raises a `ValueError` (`"queue_dir escapes workspace: {queue_dir}"`), preventing the conversation queue from writing agent entries outside the workspace.
- The `http_request` action handler now protects against Server-Side Request Forgery (SSRF). By default it blocks requests to private/reserved IP ranges (e.g. `localhost`, `127.0.0.1`, `169.254.169.254`, `10.0.0.0/8`, IPv6 loopback/unique-local/link-local, and IPv4-mapped IPv6 addresses) by resolving the host and checking each resolved IP. Optional `allowed_hosts` and `blocked_hosts` params (hostname patterns with `*` wildcards) restrict or deny specific hosts, and `resolve_private_ip` (default `true`) can be set to `false` to disable the private-IP check for internal pipelines.
- The issue-fix plugin's `_cleanup_stale_task` now validates that the task directory is contained within `TASKS_DIR` (using `is_relative_to`) before deleting it with `shutil.rmtree`. A task directory that escapes `TASKS_DIR` (via `..` segments, absolute paths, or symlinks) is rejected with an ERROR message and the cleanup is aborted (returns `False`), preventing path traversal attacks that could delete arbitrary directories outside the tasks directory.
- The issue-fix plugin's `_finalize_issue_outcome` now sanitizes the issue ID through `issue_filename()` before constructing the issue file path (`.SWE/issues/{id}.md`), instead of using the raw issue ID directly. An issue ID containing `..` (e.g. `../../escape`) now raises a `ValueError` instead of writing an issue file outside the issues directory, preventing path traversal attacks via malicious issue IDs.
- Symlink marker creation (`create_marker` for SYMLINK markers) is now TOCTOU-safe: it opens the parent directory with `O_DIRECTORY|O_NOFOLLOW` (so a directory component swapped for a symlink after path validation fails the open rather than being followed), creates the symlink at a temporary name (`.{name}.tmp{pid}`), and atomically renames it into place with `os.replace`, eliminating the race window between unlink and symlink creation. Temp symlinks are cleaned up if the rename fails.
